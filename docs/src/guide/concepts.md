# Core concepts

## Every node is an `ast-node`

`ast-node` is the base structure and carries only the things every node has:
an optional source location (`ast-source-file`, `ast-source-line`,
`ast-source-column`) and the namespace/import context (`ast-namespace`,
`ast-imports`). Its `:conc-name` is `ast-`, which is why the accessors read
`ast-source-line` rather than `ast-node-source-line`.

Concrete node kinds include `ast-node` directly or through one of two
intermediate structures. They cover expressions, binding forms, control flow,
multiple values, conditions, and CLOS:

| Intermediate | Includes | Used by |
|---|---|---|
| `ast-callable` | params, optional-params, rest-param, key-params, declarations, body | `ast-lambda`, `ast-defun` |
| `ast-local-fns` | bindings, body | `ast-flet`, `ast-labels` |

The structures are generated by the `define-ast-nodes` macro in `src/nodes/ast.lisp`.
It expands to one ordinary `defstruct` per entry and adds nothing else; it
exists to keep the `(:include ast-node)` boilerplate from burying the slots,
which are the only part that varies.

## The data protocol is the single source of truth

`ast-children` and `ast-bound-names` provide the shared data protocol for tree
structure and binding names.

`ast-children` returns a flat list of a node's child sub-expressions.
`ast-bound-names` returns the names newly introduced by a binding form.
Variable-binding forms return variable names; `flet` and `labels` return local
function names.

Structural traversal uses `ast-children`; binding-sensitive passes also use
`ast-bound-names` or rules for specific binding forms. `find-mutated-variables`,
`find-free-variables`, escape analysis, and the generic recursion inside
`find-captured-in-children` descend through `ast-children` rather than
re-deriving child structure with their own `typecase`.

When adding a node kind, define its `defstruct` and add an `ast-children` clause.
For a binding form, also add an `ast-bound-names` clause and explicit handling
in each analysis whose result depends on its scope. Generic structural
traversals then visit its children, while binding-sensitive rules stay in the
analyses that need them.

!!! note "Round-tripping is not part of the protocol"

    `ast-to-sexp` is a generic function with one method per node type, not a
    `ast-children` walk. Printing has to know each form's concrete syntax —
    where the bindings go, which parts are a lambda list — so there is nothing
    generic to share. A missing method is a loud `no-applicable-method` error
    rather than a silently half-printed tree.

## Free, bound, mutated, captured, escaping

Closure conversion needs five distinct questions answered about a variable,
and `src/closure-analysis/closure.lisp` keeps them as separate helpers rather
than combining them in one analysis pass:

- **Bound** — `ast-bound-names`: names introduced by this form, which can be
  variable names or local function names.
- **Free** — `find-free-variables`: referenced but not bound within this
  subtree, so a closure over it must capture it.
- **Mutated** — `find-mutated-variables`: a `setq` target. If an inner closure
  captures it, copying the value would lose later updates.
- **Captured** — `find-captured-in-children`: a variable of *this* scope that
  some inner lambda, `defun`, `flet` or `labels` closes over, so it may need
  boxing.
- **Escape tags** — `binding-escape-kinds-in-body` classifies AST uses.
  `:return` marks a visited variable node, not a control-flow return;
  `:capture` marks references across a closure boundary; `:external-call` marks
  uses passed to `apply`, `funcall`, or a call not classified as safe. These
  tags describe AST structure, not proven runtime escapes. See the
  [API reference](../reference/api.md#binding-escape-kinds-in-body) for the
  exact rules and `safe-consumers` behavior.

See [Recipes](recipes.md) for free-variable and escape-predicate examples.
