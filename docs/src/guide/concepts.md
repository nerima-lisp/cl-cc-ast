# Core concepts

## Every node is an `ast-node`

`ast-node` is the base structure and carries only the things every node has:
an optional source location (`ast-source-file`, `ast-source-line`,
`ast-source-column`) and the namespace/import context (`ast-namespace`,
`ast-imports`). Its `:conc-name` is `ast-`, which is why the accessors read
`ast-source-line` rather than `ast-node-source-line`.

Concrete node kinds — roughly forty of them, covering expressions, binding
forms, control flow, multiple values, conditions, and CLOS — `:include` it,
either directly or through one of two intermediate structures:

| Intermediate | Includes | Used by |
|---|---|---|
| `ast-callable` | params, optional-params, rest-param, key-params, declarations, body | `ast-lambda`, `ast-defun` |
| `ast-local-fns` | bindings, body | `ast-flet`, `ast-labels` |

Those two exist so that a pass can say "this is a callable boundary" or "this
is a local function form" once, rather than enumerating the concrete types.
`find-captured-in-children` is written exactly that way.

The structures are generated by the `define-ast-nodes` macro in `src/ast.lisp`.
It expands to one ordinary `defstruct` per entry and adds nothing else; it
exists to keep the `(:include ast-node)` boilerplate from burying the slots,
which are the only part that varies.

## The data protocol is the single source of truth

Two functions describe the shape of the tree, and nothing else is allowed to.

`ast-children` returns a flat list of a node's child sub-expressions.
`ast-bound-names` returns the variable names a node newly binds, and is
meaningful only for binding forms — `let`, `lambda`, `defun`, `flet`,
`labels`, `multiple-value-bind`.

Every traversal in the system is built on those two:
`find-mutated-variables`, `find-free-variables`, the escape analysis, and the
generic recursion inside `find-captured-in-children` all descend through
`ast-children` rather than re-deriving structure with their own `typecase`.

The practical consequence is where you edit when the language grows. Adding a
node kind means adding a `defstruct` entry and a clause to `ast-children` (plus
`ast-bound-names` if it binds anything). Every existing analysis then handles
it. Adding a node kind and teaching each pass about it separately is the
failure mode this protocol exists to prevent.

!!! note "Round-tripping is not part of the protocol"

    `ast-to-sexp` is a generic function with one method per node type, not a
    `ast-children` walk. Printing has to know each form's concrete syntax —
    where the bindings go, which parts are a lambda list — so there is nothing
    generic to share. A missing method is a loud `no-applicable-method` error
    rather than a silently half-printed tree.

## Free, bound, mutated, captured, escaping

Closure conversion needs five distinct questions answered about a variable,
and `src/closure.lisp` keeps them as five separate predicates rather than one
"analyse" pass:

- **Bound** — `ast-bound-names`: introduced by this form.
- **Free** — `find-free-variables`: referenced but not bound within this
  subtree, so a closure over it must capture it.
- **Mutated** — `find-mutated-variables`: the target of a `setq`, so it cannot
  be captured by value.
- **Captured** — `find-captured-in-children`: a variable of *this* scope that
  some inner lambda, `defun`, `flet` or `labels` closes over, so it may need
  boxing.
- **Escaping** — `binding-escape-kinds-in-body`: the binding leaves this body,
  by being returned (`:return`), closed over (`:capture`), or passed to
  `apply`, `funcall`, or an unknown callee (`:external-call`).

The escape analysis is deliberately conservative and intra-procedural: when it
cannot see where a value goes, it reports an escape. `:safe-consumers` is the
escape hatch, a list of uppercase function names a caller certifies as
non-escaping consumers.

See [Recipes](recipes.md) for what these look like in use.
